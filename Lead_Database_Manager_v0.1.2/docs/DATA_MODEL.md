# Модель данных

## 1. Идентификаторы и связи

- `leads.id` — внутренний UUID.
- `leads.telegram_id` — Telegram ID в виде TEXT, UNIQUE.
- `segments.id` — UUID раздела.
- `lead_segments` — связь многие-ко-многим. Составной PK `(lead_id, segment_id)` предотвращает повторную привязку.
- `chat_queue.idempotency_key` — уникальный ключ бизнес-действия, не только Telegram update ID.

## 2. Основные сущности

| Таблица | Назначение | Этап |
|---|---|---|
| `leads` | Центральная карточка пользователя | 1 (минимальная), 3 (полная CRUD-модель) |
| `segments` | Логические разделы базы | 3/6 |
| `lead_segments` | Принадлежность лида к разделам | 3/6 |
| `consent_events` | История согласия/отзыва | 1 |
| `telegram_updates` | Идемпотентность входящего webhook | 1 |
| `search_jobs` | История поисковых/импортных заданий | 3/8 |
| `chat_queue` | Очередь разрешённых коммуникаций | 3/9 |
| `chat_history` | История коммуникаций | 3/9 |
| `app_users` | Пользователи веб-приложения и роли | 10 |
| `settings` | Системные параметры | 2/10 |
| `audit_log` | Журнал действий пользователя/системы | 2/5/10 |

## 3. Рекомендуемые поля `leads`

| Поле | Тип | Правило |
|---|---|---|
| id | TEXT | UUID PK |
| telegram_id | TEXT | UNIQUE, NOT NULL |
| username | TEXT | nullable, индекс с NOCASE |
| first_name | TEXT | nullable |
| last_name | TEXT | nullable |
| source | TEXT | идентификатор источника |
| quality | TEXT | high / medium / low / unclassified |
| status | TEXT | new / in_progress / processed / qualified / rejected / blocked |
| consent_status | TEXT | none / granted / revoked; отдельный от status |
| consent_at | TEXT | дата последнего согласия |
| consent_source | TEXT | канал/версия уведомления/механизм |
| extra_json | TEXT | расширяемые атрибуты; только валидированный JSON |
| created_at | TEXT | UTC ISO-8601 |
| updated_at | TEXT | UTC ISO-8601 |

Точная конечная схема будет оформлена numbered migration в этапе 3. Изменения не должны ломать уже сохранённые данные.

## 4. Инварианты

1. Один `telegram_id` — максимум одна строка `leads`.
2. Лид не добавляется в центральную базу до получения подтверждения согласия для этого канала сбора.
3. Отзыв согласия не удаляет историю согласия и не должен удалять саму карточку без отдельного действия администратора.
4. Пользователь может состоять в нескольких разделах.
5. Удаление сегмента удаляет только связи сегмента; сами лиды остаются.
6. Нельзя отправлять коммуникацию, если `consent_status != 'granted'`.
7. Все массовые действия выполняются ограниченными пакетами и журналируются.
