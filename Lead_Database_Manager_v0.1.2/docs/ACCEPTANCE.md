# Протокол проверки и приёмки — этап 1 (v0.1.1)

## Проверка пользователем без установок

1. Распаковать ZIP.
2. Открыть `START_HERE.html` двойным щелчком.
3. Перейти по кнопке в интерфейс.
4. Убедиться, что страница, стили и скрипты загрузились.
5. Убедиться, что интерфейс явно показывает offline preview и не утверждает, что D1/Worker/Telegram подключены.
6. Убедиться, что поле webhook настройки недоступно в локальном preview.

## Автоматические проверки в среде разработки

- JavaScript unit tests: `node --test tests/*.test.js`.
- SQLite migration/schema tests: `python tests/sqlite_schema_test.py`.
- JavaScript syntax check: `node --check src/worker.js`.
- Проверка состава архива и повторного чтения ZIP.

Эти команды предназначены для среды разработки и не требуются пользователю.

## Ручная проверка после публикации на Cloudflare

1. `GET /api/health` возвращает `200`, `checks.database = connected`, `leads_count = 0` для пустой базы.
2. Без секретов Telegram health показывает `not_configured`; секреты в браузер не попадают.
3. Регистрация webhook с неверным `SETUP_TOKEN` возвращает `401`.
4. Регистрация с верным token вызывает `getMe` и `setWebhook`, возвращает username бота.
5. Запрос к webhook без правильного `X-Telegram-Bot-Api-Secret-Token` возвращает `401`.
6. Отправка `/start` боту выводит текст согласия и две кнопки.
7. До нажатия «Согласен» таблица `leads` остаётся пустой.
8. Нажатие «Не согласен» не добавляет лида.
9. Нажатие «Согласен» создаёт одну запись `leads` и событие `consent_events`.
10. Повтор одного и того же update не создаёт дублирующую запись.
11. `/stop` меняет `consent_status` на `revoked` и записывает consent event.

## Что не подтверждено локальным предпросмотром

Предпросмотр из файла не выполняет сетевые запросы, не подключается к D1 и не обращается к Telegram. Фактический cloud integration test возможен только после публикации в аккаунте пользователя и настройки D1 binding/secrets.
