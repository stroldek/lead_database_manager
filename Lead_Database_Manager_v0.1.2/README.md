# Lead Database Manager — v0.1.2

**Этап 1/12: техническое проектирование и проверка возможностей**  
**Поставка:** полный ZIP-проект с предпросмотром в браузере и публикацией через GitHub + Cloudflare.

## Важно: ничего не устанавливать на компьютер

Для локального просмотра интерфейса:
1. Распакуйте ZIP.
2. Откройте `START_HERE.html`.
3. Нажмите «Открыть интерфейс проекта».

Node.js, Python, Docker, Wrangler, Git и редактор кода на компьютере не требуются. В Cloudflare Wrangler запускается в облачной сборочной среде — предупреждение `npm warn exec` в логе Cloudflare относится к серверу сборки, не к вашему компьютеру.

## Исправление структуры для GitHub / Cloudflare

**В этой версии все файлы проекта находятся непосредственно в корне ZIP.** После загрузки файлов в GitHub в корне репозитория должны быть видны:

- `wrangler.jsonc`
- `package.json`
- `public/`
- `src/`
- `migrations/`
- `docs/`

Не загружайте папку `lead_database_manager_v0.1.2` целиком как вложенную папку репозитория. Загружайте её содержимое в корень репозитория. В противном случае Cloudflare может не увидеть `wrangler.jsonc` и каталог `public`.

## Настройки Cloudflare Workers Builds

В настройках сборки репозитория:

- **Root directory:** `/` (корень репозитория; оставить значение по умолчанию, если поле пустое).
- **Build command:** пусто / не задавать.
- **Deploy command:** `npx wrangler deploy --config ./wrangler.jsonc`.

`wrangler.jsonc` явно указывает Worker entry point `./src/worker.js` и каталог статических файлов `./public/`. Это штатная конфигурация Cloudflare Workers Static Assets.

## Почему D1 binding пока не включён

В предыдущей версии в Wrangler config находился примерный текст `REPLACE_WITH_D1_DATABASE_ID`. Это не настоящий ID вашей базы и могло стать следующей ошибкой после исправления пути к assets. В v0.1.2 первоначальная публикация Worker не зависит от D1 ID: интерфейс и Worker должны развернуться, а статус базы будет честно отображаться как «нет binding».

Когда Worker успешно опубликуется, следующим шагом создадим D1 в Cloudflare Dashboard и добавим её реальный binding `DB` в конфигурацию следующей сборки. SQL миграция уже находится в `migrations/0001_stage1_prototype.sql`.

## Проверка публикации

После успешного deploy:
1. Откройте адрес `*.workers.dev`, который покажет Cloudflare.
2. Должен открыться интерфейс Lead Database Manager.
3. Worker API проверяется по адресу `/api/health`.
4. До подключения базы статус D1 должен быть «Нет binding» — на этом шаге это ожидаемо.

## Что входит в v0.1.2

- Worker API: health-check и Telegram webhook.
- Проверка секрета Telegram webhook.
- `/start`, `/help`, `/stop` и inline-согласие.
- Фиксация согласия и отзыв согласия.
- Защита от повторной обработки Telegram updates.
- Тёмный интерфейс статусов.
- Локальный browser preview.
- Конфигурация Cloudflare Workers Static Assets.

## Технические проверки

Тесты предназначены для среды разработки и сборки, запускать их на компьютере пользователя не нужно:
- `node --test tests/*.test.js`
- `python tests/sqlite_schema_test.py`
- `node --check src/worker.js`

Реальное подключение к аккаунту Cloudflare и Telegram можно подтвердить только после публикации и настройки секретов.

## Ограничения Telegram

Telegram Bot API не позволяет боту начинать диалог с произвольным пользователем. Пользователь должен сам инициировать взаимодействие, а сохранение профиля в текущем прототипе происходит только после явного согласия. Команда `/stop` отзывает согласие.
